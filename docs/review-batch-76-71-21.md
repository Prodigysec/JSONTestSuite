# Value observations and V8 coverage: #76, #71, #21

Reviewed on 2026-10-03. Upstream [#76](https://github.com/nst/JSONTestSuite/issues/76) asks to compare how parsers handle negative and positive zero; [#71](https://github.com/nst/JSONTestSuite/issues/71) asks to expose case-insensitive object-key handling; [#21](https://github.com/nst/JSONTestSuite/issues/21) requests broader C++ parser coverage, including V8. The three issues remain open and have no PR revisions to integrate. The local four transformation fixtures were added in the [earlier review](review-batch-77-76-71.md); this batch leaves their bytes unchanged.

Local integration commit: `0786e4b`.

`python3 -B run_transform.py` now emits four JSON Lines records, each with separate Python and Node/V8 observations. It reads the exact fixture bytes with strict UTF-8 decoding and parses one complete JSON text. For `[0.0]` (`5b 30 2e 30 5d 0a`) and `[-0.0]` (`5b 2d 30 2e 30 5d 0a`), it reports the parsed sign bit and the serialized text separately. Both tested runtimes retain the negative sign in the parsed value. Python 3.12.3 serializes these arrays as `[0.0]` and `[-0.0]`; Node 24.21.0 / V8 13.6.233.17-node.53 serializes both as `[0]`. This is an observed representation difference, not a syntax failure: RFC 8259 §6 allows the `-0.0` spelling but does not require a particular in-memory zero representation or round trip.

For `{"a":1,"A":2}` and `{"A":2,"a":1}`, both runtimes report two distinct members in their original order, with `a = 1` and `A = 2`. These files have no final newline. RFC 8259 §4 discusses unique member names, and §8.3 describes code-unit comparison for interoperable name matching; ASCII `a` and `A` differ. The command records parsed members and serialization instead of treating exit status alone as a value assertion. A missing Node runtime is marked `unavailable`; malformed input, observer errors, and timeouts are explicit statuses.

For #21, the registry already has `Node.js V8 JSON.parse (strict UTF-8)` from the [earlier runtime review](review-batch-39-25-83.md). The existing adapter was rechecked on a valid scalar, extra comma, trailing garbage, and malformed UTF-8, then surveyed across all 327 parsing fixtures with a five-second bound: 288 expected `y_`/`n_` outcomes, 25 `i_` acceptances, 14 `i_` rejections, and no unexpected outcomes, crashes, or timeouts. Node uses a V8 engine, but this exercises the JavaScript `JSON.parse` API through Node, **not** V8's native C++ embedding API. It therefore gives a V8 comparison without completing #21's broader C++ library request; folly/json and JSON Spirit remain unreviewed. Node's own [V8 API documentation](https://nodejs.org/api/v8.html) identifies the V8 version as part of the Node binary.

The focused observer does not execute the other 22 transformation fixtures, make general cross-parser value verdicts, or regenerate `results/transform.html`. Historical parsing reports remain untouched.
